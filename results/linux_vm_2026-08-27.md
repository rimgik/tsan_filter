# Linux/AArch64 VM evaluation — 2026-08-27

These are development results from an Ubuntu 24.04 AArch64 Lima VM with four
virtual CPUs, 8 GiB RAM, and 4 KiB pages. They validate Linux behavior and
expose implementation costs, but native Linux is still required for final PMU
measurements.

## Compared builds

- Stock: pristine parent commit `73e729f7b2f030390095db1eaa162cbd666be3e7`.
- Candidate: `feat/linux-evaluation` with the one-word filter enabled at
  compile time and `TSAN_OPTIONS=one_word_filter=1` at run time.
- Both: Release AArch64 builds, Clang plus compiler-rt, `-O1`, and static TSan.

A candidate binary with the runtime option disabled was rejected as the stock
baseline because its compiler instrumentation is different. Stock-versus-stock
calibration showed about 0.9% median separation.

## Linux fast-path correction

On AArch64 47/48-bit Linux mappings, the fixed heap range is empty and malloc
storage is in high application memory. The first Linux port mapped low, heap,
and high ranges. That made the inline path perform three range checks and a
three-way note-index calculation.

The revised mapping keeps only low memory and one secondary range: the fixed
heap where it exists, otherwise high application memory. This covers Linux
allocations with the original two-range probe. The private-loop median changed
from 0.5905 s with the three-range check to 0.3944 s with the two-range check.

## Correctness

- LLVM instrumentation test: passed.
- Focused runtime test: private hit, ownership revocation, and race handover
  passed.
- Full `check-tsan`: 356 passed, 102 unsupported, 2 expected
  failures, and no unexpected failures.
- Redis and SQLite runs below reported no races.

## Performance

### Deliberately favorable private loop

One heap cell, 300 million writes, seven warmed and interleaved repetitions:

| Variant | Median timed loop |
| --- | ---: |
| Stock TSan | 0.5427 s |
| One-word filter | 0.3944 s |

The filter is about 27% faster, or 1.38x. Stock still emits a
`__tsan_write8` call on every iteration; it is not using escape analysis to
remove instrumentation. This result shows that a repeated exact note hit can
beat the callback, not that the filter is generally faster.

### Redis 8.8 server

The server and client were pinned to disjoint CPU sets. Each measured run used
100,000 requests for SET, GET, and INCR with 20 clients and two Redis I/O
threads. Five warmed, interleaved repetitions:

| Variant | Median mean throughput | Median peak RSS |
| --- | ---: | ---: |
| Stock TSan | 91,351 req/s | 41,688 KiB |
| One-word filter | 63,123 req/s | 59,480 KiB |

The filter has about 31% lower throughput and 43% higher peak RSS. An earlier
unpinned series was discarded because the same stock binary ranged from about
59k to 132k req/s.

### SQLite speedtest1

In-memory `main` test set at size 25, five warmed and interleaved repetitions:

| Variant | Median wall time | Median peak RSS |
| --- | ---: | ---: |
| Stock TSan | 5.76 s | 112,908 KiB |
| One-word filter | 9.92 s | 124,520 KiB |

The filter is about 72% slower and uses about 10% more peak RSS.

## Interpretation

The best case now works on Linux, but the real programs expose the design's
main cost. A matching note avoids the TSan callback. A nonmatching note pays
for the inline range calculation and atomic note load, then falls back and
pays ordinary TSan as well. General code has enough misses and additional note
traffic that the hit savings do not recover that cost.

The 4 KiB Linux page size is relevant to large mappings and TLB behavior, but
not to the one-cell timed loop: allocation tagging and the initial store occur
before timing, so its pages are already resident. Cache and IPC attribution
remains unmeasured because the VM does not expose hardware PMU counters.
